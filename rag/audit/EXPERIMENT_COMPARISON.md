# Experiment comparison — chunking, embeddings, retrieval, reranking, combinations (audit 2026-10-15)

All numbers below are **recomputed from the stored per-query results** by `recompute.py` (they match every stored
summary exactly) unless marked otherwise. Full matrix of all 58 measured configuration rows: `EXPERIMENT_MATRIX.md`
(generated by `build_comparison.py`). Setting: development set of 42 reviewed queries; "Matcher" = ESCO + job-filtered
queries pooled (n = 40), "all-jobs" = search across all 20 postings (stress test, n = 24), French subset n = 6.
**All results here are development-set results.** The only held-out numbers are the exp02 holdout (30 queries,
2 configurations, now inspected and no longer usable as a clean test).

Status legend: **V** = previously measured and verified by recomputation; **N** = newly measured in this audit;
**NT** = not tested; **B** = blocked.

\* index time includes encoding the 1,621 ESCO entries (~45 s), identical for every chunker.

Real-posting example (`chunking_examples.md`, posting usajobs-883337000, probe = the GS-14 four-item AND list):
fixed and sentence chunking split the list over 2 chunks; structure, recursive, sliding, semantic and parent-child
keep it in one unit; only structure and parent-child keep the `Job | Section` header.

**Why structure-300 was selected and whether that still holds**: it has the best Matcher MRR among single-vector
chunkers, keeps requirement lists and section context together, returns a citable section label, and is cheap
(197 vectors). 150 words is worse (−0.060 MRR; the CI excludes 0 with seed 0 but touches 0 with seed 1); 500 words is
slightly worse. Parent-child is the only chunker ahead (3-sentence: +0.037, CI [−0.013, +0.100], p = 0.38;
Holm-adjusted p = 1.0). The evidence still supports structure-300 as default; parent-child is the most promising
change and should be re-tested on the final test set.

Hybrid search does **not** help on this corpus: RRF lowers ESCO MRR (BM25 promotes lexically similar but wrong
concepts) and does not raise Matcher MRR. BM25 is strong on exact job wording (job-filtered 0.844) but weak on ESCO
synonyms and fails French queries (0.333). BM25 remains available as fallback (`mode="bm25"`, no model needed).

setting (diminishing returns). They still matter for all-jobs search.
